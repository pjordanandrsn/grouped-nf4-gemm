# Audit: RTX A2000 timings presented as speed evidence (2026-10-05)

*Record, unanchored. Companion audit: experts4bit-qlora `docs/audits/a2000-timing-2026-10-05.md`, which states the rule,
the method and the classes in full. Line numbers are `origin/main` at `9622144`, before this audit's own edits.*

**The rule audited.** The RTX A2000 (QNAP .68, a shared production box) is a correctness testbed only. The owner set this
on 2026-07-27 and re-stated it on 2026-10-05. An A2000 timing may not seed a prediction, filter a candidate, or appear as
speed evidence, whatever its label.

**Classes.**

- **a**: correctness, bytes, counts, or the policy itself.
- **a-nt**: an A2000 timing quoted only to show it does not transfer.
- **b**: an A2000 timing presented as a reading or comparison.
- **c**: an A2000 timing used as the basis of a band, a default, a plan, a filter or a verdict.

Two read-only classifiers covered the `kernel/`, `bench/`, `docs/` and `router_probe/` PREREG and RESULTS records.
`kernel/*.py` comments, README, STATUS, the Unreleased CHANGELOG, `docs/` and the register were reviewed in this session.

**Already fixed today (not redone here).**

## 2. For the owner (not applied: each changes a README/STATUS headline or is a code change)

**`gnf4.kernel.dgrad`.**

- **The row.** Measured. Value "403.7 -> 26.5 ms per step, E=256"; hardware "A2000 (sm_86)".
- **Where it is quoted.** README.md:247 and docs/STATUS.md:38 (results tables), CHANGELOG 0.7.0 (released).
- **The issue.** The headline is an A2000 timing.
- **Recommended: relabel as non-speed.**
  - Keep the id. Make the value the correctness result already in the claim: one launch, gradient ~2.9e-3 from the
    exact loop, inside the bf16 budget.
  - Change the two table rows to match.
  - If a speed headline is wanted, add a row with cross-repository evidence on experts4bit-qlora's
    `bench/dgrad-gate/RESULTS-dgrad-gate.md`: Qwen3-30B-A3B at 48 layers on a rented RTX A6000, published wheels, the
    fused step at 2.52x the reference loop with dgrad and 1.72x without.
- **Alternative:** retire the row with `retired_reason` "an A2000 timing; the A2000 is a correctness-only testbed". This
  stretches the schema's "known to be wrong".

**`gnf4.serve.int4-b32-splitk-row-term.a2000.2026-09-10`.**

- **The row.** Measured. Value "1.011 x the per-cell optimum over 48 cells (the N-only rule: 1.136x)", read on the A2000.
- **Where it is quoted.** STATUS.md:258-270; capabilities.json:284 and :291; `docs/solutions/int4-decode-gemv.md:120`;
  CHANGELOG 0.31.0 (released).
- **The issue.** It is the only receipt for a live plan: `SPLITK_R_TERM_MAX_SMS = 64` keeps the R term on for every part
  with 64 SMs or fewer "so the measured class keeps the win".
- **Recommended.**
  - Retire the row, with the reason above.
  - Before touching the gate, rent one ≤64-SM card (an L4 has 58 SMs, an RTX A4000 48) for P39's step-level H1 read.
    That is ~$0.10-0.30.
  - Then either keep the term with a rented receipt, or set the gate so no part takes it. Flipping it changes
    split-K grouping on those parts, which is reorder-class, not bitwise.
  - capabilities.json:291 describes behaviour and can stay. It drops or re-labels the claim citation together with
    STATUS and the solution page.

**`kernel/test_int4_b32.py:684` and :805-828.**

- **The issue.** `SK_R_BOUND = 1.07` and `test_plan_beats_the_n_only_rule_on_the_swept_cells` assert the plan against
